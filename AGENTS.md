# AGENTS.md

Guidance for Claude Code (claude.ai/code) when working in this repository.

## Before Starting Work

- Confirm whether the task is a **feature, bugfix, or refactor**.
- Check whether it touches the **public config schema** (`src/lib/config/configs`).
- Decide whether it needs **new tests** (default: yes for any new logic or a
  bugfix with a reproduction case — see **Definition of Done**).
- Decide whether it needs **doc updates** (README, `docs/`, or schema).
- For unfamiliar areas, skim `README.md` and `docs/` first.
- Plan to run `oxfmt`, `oxlint`, and the test suite before finishing (see
  **Definition of Done**).

## Guardrails

What is and is not enforced — this is the part most worth internalising.

| Check  | Command                       | Enforced?                                                                                                            |
| ------ | ----------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Types  | `pnpm build` / `tsc --noEmit` | **Yes, hard-fails.** `noEmitOnError` in the base config blocks emitting broken code, and `nest build` exits non-zero |
| Format | `pnpm format:check`           | **Yes.** oxfmt also reformats markdown tables — run it on `.md` too                                                  |
| Lint   | `pnpm lint`                   | **Partially.** oxlint, warnings only, tiny rule set                                                                  |
| Tests  | `pnpm test`                   | Only what you run; nothing blocks a commit                                                                           |

- **`no-explicit-any` is not enforced anywhere.** It appears in `.oxlintrc.json` only as an
  `off` override for spec files, and the base ruleset never enables it. A new `as any` in
  production code will not be flagged. `noUnusedLocals` _is_ enforced, so a cast left behind
  after deleting code will fail the build.
- **Unused imports fail the build** (`noUnusedLocals: true`). Remove them when you remove
  the last usage, or `tsc` will error.
- **`strict: true`, but relaxed in two places** by the Nest preset:
  `strictPropertyInitialization: false` (hence the `!` markers on DI fields like
  `protected searchField!`) and `noUncheckedIndexedAccess: false`. Non-null assertions are
  therefore _not_ required for indexed access here, unlike in the base config.
- **Never suppress a type error with `as any` to make the build green.** If a library
  generic resists, pin the type arguments explicitly or cast to the precise library type.
  See `BaseRepository.findAndPaginate` (threads MikroORM's `Using` generic) and
  `BaseService.create` (`create<false, CreateEntityType<Entity>>`) for the pattern.
- **`pnpm-lock.yaml` is committed.** Never hand-edit it and never let npm or yarn touch the
  tree — regenerate via `pnpm install`.
- **Barrel `index.ts` files marked `// This is autogenerated file, edit if only you are sure`
  may be overwritten.** Export from the underlying module instead.
- **Don't reformat unrelated files.** Run `npx oxfmt <path>` on just what you touched rather
  than `pnpm format` across the repo, to keep diffs reviewable.
- **`CLAUDE.md` was replaced by `AGENTS.md`** in this working tree. If a tool looks for
  `CLAUDE.md`, symlink it rather than duplicating the content, or the two will drift.
- Do not run any destructive/system-modifying command unless the user explicitly asks for it.
- Do not revert user changes unless explicitly asked.
- Do not edit generated files (docs build output, i18n generated files`) directly — regenerate them via their command instead.
- `config schema (src/lib/config/configs)` is the source of truth for config shape. Never let `.env` drift from it silently — update all two
  together.
- Don't commit, push, or open a PR unless asked to.
- When in doubt about scope, prefer the smaller change and ask.

## Editing Conventions

- Match the surrounding code. Do not reformat, reorder imports, or restructure code you
  were not asked to touch — it buries the real change.
- Preserve runtime behaviour unless the task is explicitly to change it. A type-level fix
  should produce a diff with no behavioural effect.
- Prefer small, focused changes over broad rewrites.
- Prefer refactors that reduce duplication and nested branching.
- Oxlint and Oxfmt is enabled — keep imports clean and avoid obvious lint noise.
- Use ASCII in code, comments, and identifiers unless the file already uses
  Unicode. This does **not** apply to intentional UI glyphs (e.g. Nerd Font /
  emoji icons in widget config defaults) — those are a design choice, not a
  style violation.

## Assistant Behavior

**Communication:**

- Be concise — respect token budgets; prioritize clarity over elaboration.
- Ground answers in code inspection, not assumptions.
- Show concrete code snippets rather than descriptions.
- Use progressive disclosure — start simple, add detail only if needed.
- Challenge assumptions — point out issues in plans or designs plainly.
- Be direct and professional. Do not add pleasantries, filler, or sign-offs to the end of responses.

**Tools:**

- Use branch/commit tools for git workflows (but don't commit/push unasked —
  see **Commit standards**).
- Use the `review` skill for PR reviews.
- Use the `diagnose` skill for bug investigations.
- Use the `tdd` skill for feature development.
- Use the `brainstorm` skill for design discussions.

**Testing**

- Write tests after adding new production behavior, and always when adding or changing behavior
- Add a regression test for every bug fix before considering the fix done.

## Commands

Run through pnpm (`pnpm build`, or `pnpm run build` where a script name collides
with a pnpm builtin).

```
pnpm build          # nest build -> dist/
pnpm start:dev      # watch mode
pnpm start:prod     # node dist/main
pnpm test           # vitest run (unit, src/**/*.spec.ts)
pnpm test:cov       # coverage -> coverage/
pnpm test:e2e       # vitest with vitest.config.e2e.ts (test/**/*.e2e-spec.ts)
pnpm lint           # oxlint
pnpm lint:fix
pnpm format         # oxfmt
pnpm format:check   # oxfmt --check
pnpm orm <cmd>      # npx mikro-orm, e.g. migration:create, migration:up, seeder:run
```

Single test: `pnpm test -- -t "name"` or `pnpm test src/modules/user/user.service.spec.ts`.

Migration / seeder / e2e tasks need a live database and env vars. The repo ships
`justfile` recipes (`just migrate`, `just quick-migrate`, `just seed`, `just test-e2e`)
that set `NODE_ENV` and seed credentials — prefer those over invoking pnpm directly.
Env files are **generated, not committed**: `pnpm sample` writes them into `env/`.

### Conventions

- Barrel `index.ts` files exist throughout; several are marked
  `// This is autogenerated file, edit if only you are sure`.
- Path aliases: `@common/*`, `@lib/*`, `@modules/*`, `@entities`, `@mocks`, `@generated`.
- Entities extend `BaseEntity` (`src/common/database/base.entity.ts`) and repositories
  extend `BaseRepository`, which is registered globally as MikroORM's
  `entityRepository` in `orm.config.ts` — inject repositories by class, no `@InjectRepository`.
- Feature services extend `BaseService` (`src/lib/crud/crud.service.ts`), which supplies
  `findAll` / `findOne` / `create` / `update` / `remove` given a `queryName` and `searchField`.
- Migrations land in `migrations/`. Seeders live in `src/common/database/seeders/`
  (`database.seeder.ts` is the configured `defaultSeeder`), even though
  `orm.config.ts` still points the seeder glob at a non-existent root `./seeders` —
  the CLI resolves them from the built `dist/` tree.

## Testing Conventions

- Unit specs are colocated: `*.spec.ts` beside source, discovered by
  `vitest.config.ts` (`src/**/*.spec.ts`).
- E2E specs live in `test/**/*.e2e-spec.ts` under a separate config.
- `globals: true` — `describe`/`it`/`expect` need no import.
- Mocks use `@golevelup/ts-vitest` (`createMock`).
- `helper-fns` and `unprofane` are aliased to their CJS entry points in
  `vitest.config.ts` because their ESM builds reference `module`/`__dirname` and
  throw when loaded as real ESM. Preserve that aliasing.
- `@typescript-eslint/no-explicit-any` is off for spec files only.

## Gotchas

- `orm.config.ts` points at `dist/entities/*.entity.js`, so ORM CLI commands and the
  REPL need a build (`pnpm build`) first.
- Formatting is enforced by oxfmt — run `pnpm format` before finishing, don't hand-tune
  line breaks.
- Renaming/removing a dependency means updating `pnpm-lock.yaml` via `pnpm install`,
  not editing package.json alone.

## Best practices

**Code review**

- Re-read your own diff before finishing. Remove debug output, dead code, and speculative abstractions.
- Keep diffs small and single-purpose. If a change mixes concerns, split it.
- Prefer boring, explicit code over cleverness. Optimize only when a benchmark or profile shows a problem.

**Maintenance**

- Review and refactor code regularly to maintain clarity, simplicity, and adherence to established patterns.
- Keep comments concise and valuable: state why, not what. Run the `unslop` skill when writing or rewriting comments.
- Run the `brainstorming` skill to generate and evaluate ideas before implementing them in code.
- Use sub-agent-driven development whenever working on multiple independent tasks.
- Never write comments that state the obvious; focus on explaining why the code exists or any non-trivial decisions.
- Always restrict comments to under 2 lines.

## Definition of Done

A task is **not complete** until the checks below pass. Run them every time
one feature or bugfix is finished — not just at the end of a large batch.

**Gates — all four must pass, and you must have run them:**

```
pnpm build          # exits non-zero on any type error
pnpm test           # unit specs only (src/**/*.spec.ts)
pnpm lint           # no NEW warnings
pnpm format:check   # clean, including .md you touched (docs/ and README are ignored)
```

Note that `pnpm test` is **not** the e2e suite. E2E lives in `test/**/*.e2e-spec.ts` behind
`pnpm test:e2e` (or `just test-e2e`) and needs a live app and database, so it is a
conditional fifth gate: run it when your change touches HTTP behaviour, auth, entities, or
migrations — and when you cannot, say so rather than reporting it green.

If any gate fails, fix the cause and re-run until all pass. Do not mark the task done with
checks failing.

**Current baseline.** As of this writing: 24 test files, 72 passed / 1 skipped, and exactly
one standing lint warning at `src/modules/auth/auth.service.ts:130`. If your run shows a
different count, you broke something — find out why before reporting done.

**Also required:**

- **Tests cover the change.** New behaviour has a test; every bug fix has a regression test
  that fails without the fix. A type-level refactor with no runtime effect may legitimately
  add none — say so explicitly rather than leaving it ambiguous.
- **No `as any` introduced.** Nothing enforces this (see Guardrails), so it is on you.
  Use the precise library type, or pin explicit type arguments.
- **No unused imports or dead code.** `noUnusedLocals` will fail the build, but check
  manually for unreachable or speculative additions too.
- **No stray files.** `git status` shows only intended changes — no scratch files,
  probes, `console.log`, or commented-out experiments.
- **Config changes are consistent.** If you touched `src/lib/config/configs`, the matching
  `.env` sample is updated in the same change.
- **Migrations** are generated via `pnpm orm migration:create`, never hand-written into
  `migrations/`, and a schema change ships with its migration.
- **Docs updated** when behaviour or config changed.

**Reporting.** State what changed, then what you ran and the result. Distinguish verified
from inferred, and flag anything you could not check (e.g. e2e) rather than implying it
passed.

## Commit standards

- Use [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <summary>`. Use `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, or `revert`.
- Write the subject in the imperative, under 72 characters, with no trailing period. Explain body details as what and why, not how.
- Do not commit unless explicitly requested.
- Keep each commit and PR scoped to a single logical change.
- Never append a footer to a commit message:
  - No `Co-Authored-By`, no `Signed-off-by` unless requested, no "Generated with", no AI tool or model names, no attribution lines of any kind.
- The same rule applies to all generated text: PR descriptions, issue reports, docs, and replies must not carry footers, signatures, or AI attribution.
